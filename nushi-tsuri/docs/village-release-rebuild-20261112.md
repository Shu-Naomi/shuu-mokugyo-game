## セーブ移行の準備

`village-save-migration.js` はゲームから読み込まない独立モジュール。保存への書き込みAPIを持たない。

- `plan(raw, { reference, otherRegions })` は旧JSONの移行案を返す。
- 村で保存した場合は、参考村の検証可能な自宅側の道へ位置・向きだけを移す案を作る。
- 他地域は明示された現行地域の一覧と照合し、座標、舟、進行を維持する。
- 独立した本番用 `villageLayoutVersion` を設け、同じ移行済みデータを再び飛ばさない。
- 試作の `referenceVillageLayout` があるデータを、黙って通常セーブとして採用しない。
- 不明な地域・レイアウト、破損JSON、重複したトップレベルキーは停止する。
- 変更するトップレベル値の範囲だけを差し替える。所持金、釣果、犬、魚預かり、未知の将来項目などの
  未変更部分は文字列のまま保持し、数値の再直列化で大きい整数を丸めない。既存mapVersionを変更しない。
- `prepareSlot` は通常の各スロットを読み、元の全バイトとバックアップ先候補を返すだけ。
  選択スロット情報、試作保存先、既存バックアップへ触れない。
- `checkSnapshot` は読んだ後の他タブ更新・削除を検出するが、成功しても `mayWrite:false`。

### 本番接続をまだ行わない理由

`localStorage` の比較後書き込みは原子的な比較交換ではない。新しいタブ同士でロックしても、
古いゲームのタブはその規約を知らず、後から通常のセーブキーへ書き戻せる。
現状のゲームの通常保存処理も毎回の世代検査を行う設計ではない。
したがって、準備したJSONをそのまま通常の `save()` に渡すだけでは安全な移行にならない。

本番接続には、古い書き手を排除する更新手順、元データの検証済みバックアップ、保存競合時の停止と
回復方法が必要。更新完了前に古い座標を新しい地形で保存してはならない。これらは未実装・未確認。

## キャッシュと更新の監査

`tools/audit-village-release.cjs --baseline <実際の公開コミット>` は読み取り専用のソース監査。
JSやゲームコードを実行せず、HTML・サービスワーカー・参照されるファイルを比較する。

- 変更されたファイルが古いURLのままでないか。
- 必要なJS・画像がプリキャッシュにあるか、実際に存在するか。
- HUD、ワーカー登録URL、キャッシュ名の版が一致するか。
- キャッシュ名が更新されているか。
- 強制アクティブ化、既存タブの引き継ぎ、旧キャッシュ削除について実ブラウザの確認が必要か。

現状の試作を監査すると失敗するのが正しい。旧URLのままの変更済みJS、未キャッシュの参考モジュールと画像、
据え置きのキャッシュ名がある。監査を通すためだけの版上げや本番接続はしていない。
静的監査が成功しても `productionReady:false` を返す。動的URLや実際のブラウザの保存内容は検査範囲外。

新規の移行21テストと監査13テスト、および既存の試作保存・旧キャッシュ保護20テストが成功。

これらはNode／DOMハーネスの検査であり、実ブラウザやスマートフォン実機の証拠ではない。
全体回帰の最終結果は復旧パッケージの検証記録に別途記載する。

所要時間は約28分53秒。全体実行のファイル一覧が確定した後に追加した来歴2テストも別途成功した。
移行・監査・来歴の重点36テストはすべて成功したが、そのうち34件は全体回帰にも含まれるため二重に合算しない。
